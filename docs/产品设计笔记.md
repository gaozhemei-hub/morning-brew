# 产品设计笔记

> 这份文件回答一个问题：**这个项目是"怎么想出来"的**，而不只是"怎么用"。
> 保留原始的需求判断、取舍理由、以及被推翻的结论。

## 1. 需求是怎么被定义的

最初的需求只有一句"帮我每天看前沿"。**如果照这个做，就会变成又一个资讯聚合器**。真正的转折点是用户的三次反馈：

1. **"得到的总结太宽泛"** → 说明问题不在"信息不够"，而在**没有筛选立场**。
   于是有了"三层人设"：不是按话题分类，而是**按读者身份决定该看什么、该问什么**。
2. **"大佬根本不认识，不知道怎么规划职业"** → 说明用户要的不是"知道发生了什么"，而是**知道谁在做什么、他为什么走到这里**。
   于是人物跟踪从"附带信息"升格为**一等公民**（建卡 + 关键转向 + 一键关注）。
3. **"看不到跳转"** → 说明知识沉淀的**可用性**比完整性更重要。
   于是加了 `↗` 标记与文末双链索引——**一个"能点但看不出来"的链接等于没有**。

**结论**：这个产品的真正需求是「**降低决策成本 + 积累可复用的认知**」，而不是「获取更多信息」。

| 条目形态 | **结论在前 + 分点核心观点** | 早期"一句话判断"信息量不足 | 未推翻 |
| 长度策略 | **先长后精** | 过早压缩丢推理链；先保密度再收紧 | 未推翻 |

| 人物匹配 | **宁缺勿错，低置信度只给搜索链接** | 点进错人的代价 > 多点一次的代价 | 未推翻（12 人里刻意拒绝 2 人） |
| 微信源 | ~~"只能自建，接受缺口"~~ | 当时调研结论 | ✅ **已推翻**：抄现成的（BestBlogs 公开实例 375 源） |

| 是否自动关注 | **只给链接，不自动关注** | 封号风险 + 那是用户的动作 | 未推翻 |

## 3. 竞品分析（原始判断）

看同类项目时，我们问的不是"谁功能多"，而是**"它优化的是哪一步"**：

| 优化目标 | 代表项目 | 局限 |
| --- | --- | --- |
| **送到眼前** | TrendRadar、newsnow、Folo、FreshRSS | 解决"看到"，不解决"记住" |
| **总结更好** | Horizon、ai-news-brief、ai-daily-pulse | 解决"读得快"，产出仍是**一次性文档** |
| **沉淀成资产** | ← **本项目** | 术语进库、人物进卡、可追溯、有健康报告 |

**关键观察**：调研过的项目**没有一个做"正文 ↔ 知识库"的双向链接**（输出形态是 markdown/HTML/Notion/RSS）。
这既是空白，也是我们的立足点——**别人优化"读什么"，我们优化"读完留下什么"**。

**但要诚实**：我们的抓取层、去重层、投递层**大量借鉴**了上述项目（见 README 竞品表 + 致谢）。
**没有这些先行项目，这个项目不会在两周内成形。**

## 4. 迭代节奏（怎么从 v0 走到 v4）

```
v0 通用雷达（21 源，一句话判断）
  ↓ 用户："太宽泛"  → 给出一份完整设计指引（现存档于 docs/规范-…）
v1 三层人设 + 指定信源 + 每层目标问题
  ↓ 用户："看不到跳转 / 大佬不认识"
v2 双链知识网（↗ 标记）+ 人物卡 + 一键关注
  ↓ 用户："GitHub 上肯定有人做过，去抄信息源"
v3 抄现成：375 候选池中接入 37 个公众号源（3 常驻 + 34 轮换）+ 第四块热榜 + 信源按星期轮值 + 候补机制
  ↓ 定时任务实测暴露问题
v4 工程加固：去重键、轮换判断顺序、.env 优先级、邮件渲染
```

**方法论**：**先跑通最小闭环 → 用真实反馈定标准 → 再扩源 → 最后工程加固**。
没有一开始就设计"完美架构"——每一步都是被上一版的真实缺陷推着走的。

## 5. 可迁移的经验

1. **用户说"不好"时，先问"缺的是什么立场"**，而不是"要不要加功能"。
2. **"能点但看不出来"的交互等于没有**——可见性是一等需求。
3. **宁缺勿错**：宁可少给一个链接，也不要给一个错的。
4. **禁止静默失败**：系统的健康状态必须能被非专家读懂。
5. **遇到"做不到"，先去搜别人做过没有**——比自己做方案快得多。
6. **让过程可见**：规范、基准样例、踩坑清单都留在仓库里，**迭代史本身就是交付物的一部分**。
